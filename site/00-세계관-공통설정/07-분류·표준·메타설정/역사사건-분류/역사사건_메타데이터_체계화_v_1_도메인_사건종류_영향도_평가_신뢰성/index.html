    9) (외부 레퍼런스 기반) 추가 개선안 — v1.1 반영

    9-1. event_type와 domains의 완전 분리(강제)

    • domains는 영향 영역 전용
    • “무슨 사건인가”는 classification.event_type로 고정

    9-2. EventSeries(사건군/시리즈) 도입

    • 전쟁/혁명/대붕괴/장기 침식은 시리즈 문서 1개 + 하위 사건 n개 구조 권장
    • classification.event_series_ref로 연결

    9-3. 시간 불확실성(근사/불확실/범위) 1급 시민화

    • 기존 세계관 달력 표기는 유지
    • 추가로 time.time_edtf(불확실/근사/범위 허용 문자열)를 둬서 정렬·검색·표준화에 사용

    9-4. 프로버넌스(provenance) 구조화

    • reliability와 별개로, “이 서술이 어디서 왔나/어떤 편집·재서술을 거쳤나”를 provenance에 기록
    • retcon(재서술) 사건에서 특히 강력

    9-5. 장소(place)를 권위 레코드(Authority)로 승격

    • 사건 문서에는 place.place_ref = [[지역 문서]] 링크를 기본으로
    • 지역 문서는 지명 이명/행정단위 변천/좌표(선택) 등을 담는 권위 레코드 역할

    9-6. actors도 권위 레코드(Authority)로 분리

    • 사건 문서 = 사건 내 role만
    • 행위자 문서(국가/기관/가문/개인) = 이명/존속기간/변천/관계망 등 “행위자 자체 메타”

    1) 사건군(EventSeries)

    EventSeries 목적

    • “단일 사건”을 넘어 **연쇄/장기국면(전쟁, 혁명기, 대전이, 봉쇄·제재 레짐, 난민 대이동 등)**을 하나의 상위 묶음으로 관리한다.
    • 사건 문서에서는 series를 참조해 검색/내러티브/국면 분석을 쉽게 한다.

    series.kind(사건군 종류) 사전(추천)

    series.kind_code(종류 코드) — 빠른 필터/정렬용(권장)

    • kind(사람이 읽는 라벨)과 별개로, 검색·자동분류를 위해 kind_code를 함께 둔다.
    • 형식: SERK-XXXX (문자열)
    kind_code의미대표 포함 사건(event_type 예시)
    SERK-STATE건국/망국/합병/독립 같은 주권 상태 연쇄ET-STATE.*
    SERK-REV혁명/쿠데타/정권 붕괴 같은 권력 변동 연쇄ET-GOV.*
    SERK-WAR전쟁/내전/군사대사태 캠페인 단위 연쇄ET-CONF.*
    SERK-DIP조약/수교/제재/동맹 같은 외교 연쇄ET-DIP.*
    SERK-LAW헌정·제도·기관 설계가 연쇄로 이어지는 입헌/제도 연쇄ET-LAW., ET-ELECT.
    SERK-ECO금융위기/국가부도/산업전환 같은 경제·재정 연쇄ET-ECON., ET-TECH.SHIFT.
    SERK-MIG난민/강제이주/개척·식민 같은 인구·정주 연쇄ET-DEM.*
    SERK-DIS재난 발생→수습→복구의 재난 연쇄ET-DIS.*
    SERK-TEC기술도약/표준/인프라 구축 같은 기술·인프라 연쇄ET-TECH.*
    SERK-REL종교 개혁/분파/박해 같은 종교 연쇄ET-REL.*
    SERK-IDEO이념 확산/선전·검열 레짐 같은 사상 연쇄ET-IDEO.*
    SERK-DIM차원/대전이/각성/침식 같은 차원·능력 연쇄ET-DIM.*
    SERK-COL식민지 네트워크/제국권 재편 같은 제국·식민 연쇄ET-DEM.COLONY., ET-DIP.

    2) 시간 불확실성(time_edtf)

    설계 원칙(엘리스 프라우셰크트용)

    • 네 달력 규칙(1년=48개월, 1개월=30일)을 감안하면, 현실의 ISO/EDTF를 “그대로” 강제하기보다 (1) 작중 표기 문자열 + (2) 정렬용 키 + (3) 불확실성 메타 3단으로 가는 게 제일 안전하다.
    • 따라서 v1.1에서는 time_edtf라는 이름을 유지하되, 실제 값은 엘리스 프라우셰크트 내부 표준으로 운용한다.

    time_edtf 필드 세트(권장)

    필드타입필수설명
    when_text문자열O네가 본문에 쓰는 “시간적 시점” 원문(작중 표기)
    sort_key문자열△정렬용(가능하면 채움)
    precision문자열△year / month / day / hour / minute / unknown
    certainty문자열△exact / circa / inferred / disputed / unknown
    range객체△기간형일 때(시작/끝)
    notes문자열△1문장 근거(왜 추정/논쟁인지)

    sort_key 형식(추천)

    • 기본: E{epoch}-{year:05}-{month:02}-{day:02}-{hour:02}-{minute:02}
    • epoch은 제1기=1, 제2기=2, 제3기=3 …로 숫자 매핑.
    • 월이 불명확하면 00, 일이 불명확하면 00.

    예시

    when_textsort_keyprecisioncertainty
    "7407년""E1-07407-00-00-00-00"yearexact
    "제2기 0년, 21월 30일, 오전 10시 30분""E2-00000-21-30-10-30"minuteexact
    "제1기 6500년(전후)""E1-06500-00-00-00-00"yearcirca
    "(추정) 기원전 5년""PRE-00005-00-00-00-00"yearinferred

    YAML 템플릿(복붙용)

    time_edtf:
  when_text: "제2기 0년, 21월 30일, 오전 10시 30분"
  sort_key: "E2-00000-21-30-10-30"
  precision: "minute"        # year/month/day/hour/minute/unknown
  certainty: "exact"         # exact/circa/inferred/disputed/unknown
  range:                       # 기간형일 때만 사용
    start: ""
    end: ""
  notes: "공식 선포 시각이 행정기록으로 남아 있음."  # 1문장

    3) provenance(서술 계보 / 편집 계통)

    provenance 목적

    • 사건 서술이 “어디서 왔고 어떻게 변형되었는지”를 남겨서, 나중에
      • 레거시 문서 vs 통합본 충돌,
      • 선전/검열 가능성,
      • 재서술(retcon) 분기 를 추적 가능하게 만든다.

    provenance.event_narrative_type(서술 유형) 사전(추천)

    type설명예시
    record(기록형)기록물 기반, 중립 서술 지향행정·군사기록 기반 사건
    chronicle(편년사형)연표/편년사에 맞춘 요약 서술“연대기” 문서
    propaganda(선전형)정당화/영웅서사 중심전시 선전/국교 교단 기록
    memoir(회고형)개인 시점, 편향 가능회고록/증언 중심
    reconstruction(재구성)자료 부족, 추론/모형 기반“추정” 사건 복원
    retcon(재서술)동일 사건의 버전/개정설정 변경 후 재작성

    provenance 필드 세트(권장)

    필드타입필수설명
    narrative_type문자열△위 사전
    source_bundle배열(객체)△참고한 문서 뭉치(레거시/통합본/외부자료 등)

    divergence객체△버전 분기(상충/대안 루트)
    notes문자열△1문장 메모

    source_bundle 객체(추천)

    | 필드 | 설명 | 예시 | |---|---| | kind | legacy / integrated / transcript / image / external_reference | | ref | 문서 링크/식별자 | | reliability_hint | 간단 힌트(“검열 가능” 등) |

    edit_chain 객체(추천)

    4) 권위 레코드(authority records): place / actors
